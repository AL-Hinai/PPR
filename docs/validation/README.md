# System validation pack

PPR decides whether a medicine dossier is technically acceptable and records regulatory decisions, so it is
validated before go-live and after every significant change, in a risk-based way (GAMP 5 approach; PPR is
custom software, category 5).

| Document | Purpose | Status |
|---|---|---|
| [urs.md](urs.md) | User requirements (URS-01 to URS-23) | Draft, to be approved by the HOD |
| [risk_assessment.md](risk_assessment.md) | What could go wrong, how likely, how it is controlled and verified | Draft |
| [iq_oq_pq.md](iq_oq_pq.md) | Installation, operational and performance qualification protocols with acceptance criteria | Protocol, to be executed |
| [traceability.md](traceability.md) | Requirement → automated tests → result, generated by `scripts/traceability.py --run` | Generated |
| [../validation_benchmark.md](../validation_benchmark.md) | Comparison with a reference eCTD validator (PQ-02) | Procedure, to be executed |
| [../assistant_data_protection.md](../assistant_data_protection.md) | Decision on where the assistant's language model runs | Decision pending |

## How the pack is kept current

1. Every change runs the automated suite (GitHub Actions, `.github/workflows/tests.yml`). It includes the
   production deploy checks and the validation benchmark set.
2. A change that adds or alters a requirement updates `urs.md` and tags its tests with
   `@pytest.mark.req("URS-nn")`.
3. Before a release: `python scripts/traceability.py --run`, re-execute the OQ items the change touches, record
   the result in the execution log of `iq_oq_pq.md`, and keep the generated matrix with the release.
4. A change to the eCTD DTDs or the GCC rules repeats the benchmark (PQ-02).
